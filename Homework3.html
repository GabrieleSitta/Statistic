Theory: the ideas behind the app
1. Why not the curve mod 17? In Homework 1 the equation y² = x³ + 7 was used modulo 17: G = (1, 5) generates only 9 points, far too few to hide anything. Here the same equation is used with the real secp256k1 numbers (a 256-bit prime p and a base point G of order n ≈ 2²⁵⁶). Only the private key is kept small, as the assignment asks.
2. Key pair. The private key is an integer d, the public key is the point Q = d·G. Computing Q from d is fast (double-and-add); going back from Q to d is the elliptic-curve discrete logarithm problem (ECDLP).
3. Shared secret. The sender picks a random r and computes S = r·Q = r·d·G. The receiver gets C₁ = r·G and computes d·C₁ = d·r·G. Both obtain the same point S without sending it.
4. From a point to a keystream. The x-coordinate of S is hashed with SHA-256 together with a block counter, giving as many bytes as the message. C₂ = M ⊕ keystream; XORing again gives M back. This is a simplified ECIES.
5. Caesar cipher. Each letter is a number 0…25: E(x) = (x + k) mod 26, D(y) = (y − k) mod 26. Other characters stay unchanged.
6. Language model. From a training corpus we count how often each letter (unigrams) and each pair of adjacent letters (bigrams) appears, adding 1 to every count so that no probability is zero.
7. χ² and confidence. For a candidate key, χ² = Σ (observed − expected)² / expected compares the letter counts with the corpus frequencies; the smallest χ² wins. The ratio second-smallest / smallest χ² measures how clear the choice is: close to 1 means uncertain.
8. Entropy and index of coincidence. Entropy H = −Σ pᵢ log₂ pᵢ measures how spread out the symbols are. The index of coincidence is the probability that two symbols drawn at random are equal: about 0.066 for English, 1/26 ≈ 0.038 for random letters, 1/256 ≈ 0.0039 for random bytes.
9. Baby-step giant-step. Write d = i·m + j with m ≈ √N. Store j·G for all j (baby steps), then compute Q − i·m·G for i = 0, 1, 2… (giant steps) until one is in the table. About 2√N operations instead of N, paid with memory.

Toy elliptic-curve encryption

The same curve equation as Homework 1, y² = x³ + 7, but over the real secp256k1 prime field, so that a message can actually be hidden. The scheme is ECIES-style: an elliptic-curve Diffie–Hellman agreement whose shared point is hashed into a keystream. The deliberate weakness is the private key d, restricted to 1 … 2¹⁸ − 1 (choose the size in the sidebar). The ephemeral key r is a full 256-bit random number.

Similarities. Both have an encryption and a decryption procedure that undo each other, and only the holder of the secret can decrypt. Both add a key-dependent mask to the message: Caesar adds the same k to every letter (mod 26), the ECC scheme XORs (adds mod 2) every byte with a keystream derived from the shared secret.

      
Differences. The mask is the whole difference. In Caesar it is constant, so equal letters stay equal and the statistics of the language pass straight through. In the ECC scheme the mask changes at every byte and is unpredictable without S. Moreover Caesar needs a secret shared in advance, while the ECC scheme only needs the receiver's public key.

Effectiveness, limitations and alternative approaches

      
    
        
  • Effectiveness. The longer the text, the closer its letter counts are to the language, so the right key stands out more and the confidence ratio grows. With a few dozen letters the χ² attack practically never fails.
    • 
        
  • Short texts are the main weakness: with a handful of letters a wrong key can look more English than the right one by chance. The confidence ratio is a useful warning.
    • 
        
  • Known language. The model assumes English. Another language, unusual vocabulary, lists of names or a text that avoids common letters can be misjudged at any length.
    • 
        
  • Only letters count. Spaces, digits and punctuation are ignored and add no information.
    • 
      

      
Alternative approaches

      
    
        
  • Exhaustive search always contains the plaintext (only 26 keys), but someone or something must recognise it. Scoring against a language model automates that step, and also works when the key space is too large to read by eye.
    • 
        
  • Most frequent letter = E is the simplest rule: one count and one subtraction. It fails whenever E is not the top letter of the excerpt.
    • 
        
  • χ² on letter frequencies uses the whole histogram, so it is much more robust for almost no extra work.
    • 
        
  • n-gram scoring (here bigrams) also uses the order of the letters: TH, HE, IN are common, QZ never appears. It needs a bigger model but is the best on short texts; trigrams and quadgrams are stronger still.
    • 
      

    

  


  
  

    

      
Attack on the restricted private key

      
The attacker knows the curve, G, the public key Q, the ciphertext (C₁, C₂) and that d < 218. The ciphertext gives no statistics, so the attack goes after the key. Once d is found, S = d·C₁ decrypts the message exactly like the receiver.

The statistical attack works because the cipher leaks the statistics of the plaintext; it would work even with a huge key space, as long as the cipher is a fixed substitution. The ECC attack works for the opposite reason: the ciphertext leaks nothing (tab 3), but the key can be found by trying candidates because there are few of them. Fixing one weakness does not fix the other.

    


    

      
Why this would not work against a properly configured ECC scheme

      
With a private key drawn uniformly from the full secp256k1 range there are n ≈ 1.16 · 10⁷⁷ ≈ 2²⁵⁶ candidates. Exhaustive search needs on average 2²⁵⁵ additions, and the best known generic attacks (baby-step giant-step, Pollard's rho) still need about √n ≈ 2¹²⁸ operations (see the table above): out of reach for any classical computer. Statistics do not help either, because the keystream comes from a hash of the shared secret and the ciphertext is uniform.

      
The word "necessarily" in the assignment matters: security depends on the configuration. A key taken from a small range, a weak random generator or a reused ephemeral key make the scheme attackable even on a strong curve. A large quantum computer running Shor's algorithm would break the discrete logarithm itself, but no such computer exists today.

    


    

      
Other attacks and weaknesses (optional)

      
Caused by the restricted key space

      
    
        
  • Exhaustive search and baby-step giant-step, shown above. BSGS needs only about 2√N operations by trading memory for time.
    • 
        
  • Precomputation: one table of all d·G breaks every public key of this scheme at once.
    • 
        
  • Small r: if the ephemeral key were also taken from a small range, the attacker would find r from C₁ = r·G and compute S = r·Q without ever touching d.
    • 
      

      
Caused by the design of the toy scheme (they remain with a large key)

      
    
        
  • No authentication. Flipping a bit of C₂ flips the same bit of the decrypted message, without knowing any key. 
    • 
      

      

      
    
        
  • Reused r. Two messages with the same r get the same keystream, and C₂ ⊕ C₂′ = M ⊕ M′ leaks the plaintexts without any key.
    • 
        
  • Bad randomness. A predictable r is as bad as a known one.
    • 
        
  • No point validation. The receiver does not check that C₁ is on the curve; in real software this has allowed invalid-curve attacks that leak the private key.
    • 
      

      
Real ECIES uses a proper key-derivation function, an authentication tag (MAC) on the ciphertext, validation of the received point and a 256-bit random private key.
