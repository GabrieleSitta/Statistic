From seed phrase to Ethereum address

m / 44' / 60' / 0' / 0 / i

    What happens when a wallet creates an address

    When we create a wallet in MetaMask or Rabby we only see 12 words and then an address starting with 0x. In between there are five different steps, each based on a different standard. Below, every step is computed live in this page, from the phrase in the sidebar. Each step has a colour that says what kind of operation it is:

    key generationkey derivationpublic-key cryptographyhashingchecksumencoding

    Step 0 · Random entropy and the 12 words (BIP-39)

    key generationencodingchecksum

    Everything starts from a random number. This is the only real key generation in the whole pipeline: all the next steps are deterministic. BIP-39 takes 128 random bits, adds a small checksum (the first 128/32 = 4 bits of SHA-256 of the entropy) and cuts the 132 bits into 12 groups of 11 bits. Each group is a number between 0 and 2047, i.e. one word of a fixed list of 2048 words. The words are just an encoding of the bits that is easier to write on paper.

    Step 1 · Mnemonic → seed (BIP-39)

    key derivation

    The words are not used directly as a key. They go through PBKDF2 with HMAC-SHA512, repeated 2048 times, with the salt "mnemonic" + passphrase. The result is a 512-bit seed. The repetitions make every guess slower for an attacker, and the optional passphrase gives a completely different wallet from the same words.

    Step 2 · Seed → private key (BIP-32 + BIP-44)

    key derivation

    BIP-32 turns one seed into a whole tree of keys. First HMAC-SHA512 with the key "Bitcoin seed" gives the master private key (left 256 bits) and a chain code (right 256 bits). Then each child key is computed from its parent with HMAC-SHA512 again. BIP-44 fixes which branch to use: m / purpose' / coin' / account' / change / index. The apostrophe means "hardened": that level uses the parent private key, so a leaked child key cannot be used to go back up the tree.

    Step 3 · Private key → public key (secp256k1)

    public-key cryptography

    This is exactly Homework 1, with real numbers: Q = k·G on the curve y² = x³ + 7, but modulo a 256-bit prime p instead of 17, computed with double-and-add. The private key k stays secret; Q can be shown to everybody, because going back from Q to k (the discrete logarithm problem) would take about 2¹²⁸ operations.

    Step 4 · Public key → address (Keccak-256)

    hashing

    The public key is 64 bytes (x and y), too long to share easily. Ethereum hashes it with Keccak-256 and keeps only the last 20 bytes of the 32-byte hash. The address is therefore a fingerprint of the public key: shorter, fixed in length, and it reveals the public key only after the first transaction.

    Step 5 · Address → checksummed address (EIP-55)

    checksumencoding

    Hex addresses are case-insensitive, so the case of the letters a–f is "free" information. EIP-55 uses it as a checksum: we hash the lowercase address (as text) with Keccak-256, and every letter whose matching hash digit is 8 or more is written in UPPERCASE. A wallet that receives a mixed-case address recomputes the pattern: if one character was mistyped, the pattern almost certainly no longer matches.

    The six pieces and what each one is for

    A useful way to read the pipeline is to ask, for each standard, what problem was it trying to solve? Each one appeared because the previous solution had a practical problem.

    BIP-39 · mnemonic and seed

    generationencodingchecksumderivation

    Problem: a 128-bit random number written in hex (32 characters) is very easy to copy wrong.

    Solution: encode it as 12 common words from a list of 2048 (11 bits each), add a checksum so most mistakes are caught, and stretch it into a 512-bit seed with PBKDF2 (2048 rounds of HMAC-SHA512).

    Why 2048 words? 2048 = 2¹¹, so each word carries exactly 11 bits; the first 4 letters of every word are unique, which helps when typing.

    BIP-32 · hierarchical deterministic keys

    derivation

    Problem: early Bitcoin wallets generated every key at random, so each new address needed a new backup.

    Solution: derive an unlimited tree of keys from one seed. A child key is (parent key + HMAC-SHA512(chain code, data)) mod n, so one backup covers every future key.

    Hardened vs normal: normal children can be computed from the parent public key (useful for watch-only wallets), hardened ones only from the private key, which is safer.

    BIP-44 · standard paths

    derivation

    Problem: BIP-32 allows any path, so two wallets could use different branches and the same seed would show different addresses.

    Solution: a fixed structure m / 44' / coin' / account' / change / index. Coin type 60 is Ether (0 is Bitcoin), so one seed can hold many coins in separate branches.

    For Ethereum the "change" level is always 0, since accounts don't use change addresses like Bitcoin does.

    secp256k1 · public-key cryptography

    public-key

    Role: it links the private key k and the public key Q = k·G, and it is the curve used for the ECDSA signatures of every transaction.

    Why an elliptic curve and not RSA? With ~256-bit keys it gives about 128-bit security, while RSA needs about 3072-bit keys for a similar level. Smaller keys and signatures matter on a blockchain where everything is stored forever.

    Ethereum took it from Bitcoin, which picked it from the SEC 2 standard.

    Keccak-256 · hashing

    hashing

    Role: it turns the 64-byte public key into the 20-byte address, and Ethereum uses it almost everywhere else too (transaction hashes, smart-contract storage, EIP-55).

    Properties we rely on: it is fast to compute, impossible to invert, and a tiny input change gives a completely different output (avalanche effect).

    Careful: it is the original Keccak, not exactly the NIST SHA3-256 (see the History tab).

    EIP-55 · mixed-case checksum

    checksumencoding

    Problem: plain hex addresses have no error detection: a single typo sends the money to a different (valid-looking) address.

    Solution: use the case of the letters as checksum bits. It's backward compatible, because old software reads the address in lowercase and still works.

    Limit: it detects mistakes, not attacks: someone can always create a fake address with a correct checksum.

    Statistical properties of the pipeline

    We generate many random wallets and look at the outputs. The question is the same as in Homework 1: which statistical properties should we expect, and which ones actually matter for security? Here the results are very different from the toy curve, because the address goes through a hash function.

    a) The BIP-39 checksum: how many random word lists are valid?

    If we pick 12 random words from the list, the last 4 bits must match the SHA-256 checksum by chance. Expected probability: 1/2⁴ = 1/16 = 6.25%. For 24 words the checksum has 8 bits: 1/256 ≈ 0.39%. So a wrong word is detected with probability 15/16 (12 words) or 255/256 (24 words).

    b) Hex digits of the addresses

    If the hash behaves like a random function, every hex digit should appear with probability 1/16. We use a χ² test with 15 degrees of freedom (critical value ≈ 25.0 at 5%). Here every cell has hundreds of expected observations, so unlike Homework 1 the test is reliable.

    c) Are 0s and 1s balanced?

    We write all the addresses in binary and count the 1s. If the hash output looks random, about half of the bits should be 1, and that is what we get.

    d) Avalanche: flip one bit of the public key

    We flip one random bit of the 64-byte public key and count how many of the 256 Keccak output bits change. For an ideal hash this follows a Binomial(256, ½): mean 128, standard deviation 8 (line). In Homework 1 the change was predictable (Q ± 2ⁱ·G); after the hash it looks random.

    e) Avalanche through the whole pipeline

    Now we flip one bit of the private key and compare the two 160-bit addresses. The public keys are related (they differ by 2ⁱ·G), but the hash hides it: about 80 bits change, following Binomial(160, ½), standard deviation ≈ 6.3.

    f) EIP-55: how many checksum bits does an address have?

    Only letters a–f can carry the checksum. Each of the 40 hex digits is a letter with probability 6/16, so the number of letters follows Binomial(40, 3/8): on average 15 checksum bits, but it varies from address to address (line = expected).

    g) EIP-55: does it catch typos?

    For each address we replace one random character with a different hex digit and check whether the checksum still passes. A typo changes the whole Keccak hash, so the new case pattern is random: it passes only if all the L letters happen to have the right case, probability (½)ᴸ ≈ 2⁻¹⁵ on average. With all-lowercase addresses (no checksum) every typo goes through.

    Which of these properties matter, and where

    • Uniform digits and balanced bits (b, c) are what we expect from a good hash. They matter because the address should not leak anything about the key, but passing these tests does not prove security: a non-secure function can also produce balanced bits.
    • Avalanche (d, e) is a hash property. secp256k1 alone does not have it (Homework 1), but the full pipeline does, because Keccak-256 comes after it.
    • Checksum statistics (a, f, g) are about error detection, not about security against attackers: 4 bits for BIP-39 and ~15 bits for EIP-55 are enough to catch accidental mistakes, but an attacker can easily search for a fake address with a valid checksum.
    • Entropy is decided only at step 0: 12 words = 128 bits, 24 words = 256 bits. No later step can add randomness, it can only keep it (ideally) or lose it.

    How we got here

    Filled dots are the dates asked in the assignment, empty ones are extra context that explains the order of the choices.

    • 1976Diffie and Hellman publish the idea of public-key cryptography.
    • 1977RSA: the first practical public-key system, based on the difficulty of factoring large numbers.
    • 1985Koblitz and Miller independently propose elliptic-curve cryptography: same security as RSA with much smaller keys.
    • 2000The SEC 2 document lists the curve secp256k1 among its recommended curves.
    • 2001SHA-2 (SHA-256, SHA-512) is standardized by NIST. SHA-256 is later used by Bitcoin and in the BIP-39 checksum, SHA-512 inside HMAC for BIP-32 and BIP-39.
    • 2009Bitcoin launches using secp256k1 for its keys and signatures.
    • 2012BIP-32: hierarchical deterministic wallets, one seed for a whole tree of keys. The same year Keccak wins the NIST SHA-3 competition.
    • 2013BIP-39: the seed can be written as 12–24 words.
    • 2014BIP-44: standard paths, so different wallets find the same accounts.
    • 2015Ethereum launches (July) using Keccak-256 as it was submitted to the competition.
    • 2015SHA-3 is published by NIST (FIPS 202, August), based on Keccak but with a different padding.
    • 2016EIP-55: mixed-case checksum for Ethereum addresses.

    The order explains a lot: Ethereum reused the wallet standards that Bitcoin had already developed (BIP-32/39/44, secp256k1) and only changed what was specific to it, the hash function and the address format. And since Ethereum started just before SHA-3 was finalized, it kept the original Keccak.

    Keccak-256 ≠ SHA3-256. They use exactly the same permutation, but when NIST standardized SHA-3 it changed the padding: before the usual final bit, Keccak appends the byte 0x01, while SHA-3 appends 0x06 (two extra "domain separation" bits saying "this is SHA-3"). One different byte at the start of the padding is enough to give completely different outputs.     Five different jobs: generation, derivation, public-key, hashing, checksum, encoding

    The assignment asks to keep these concepts separate. The easiest way for us was to ask two questions for each step: does it create something new or compute it from something existing? and can it be reversed?

    ConceptWhat it doesWhere in the pipelineReversible?
    key generationCreates new secret randomnessThe 128/256 random bits at step 0 (only here)Nothing to reverse: it is the starting point
    key derivationComputes new keys deterministically from existing secret materialPBKDF2 (words → seed), BIP-32 (seed → tree), BIP-44 (which branch)No, it uses one-way functions (HMAC)
    public-key cryptoPair of keys linked by a hard mathematical problem; allows signaturessecp256k1: Q = k·G, and ECDSA signatures of transactionsOnly with the private key (ECDLP)
    hashingFixed-length fingerprint of any input, no key involvedKeccak-256 (address, EIP-55), SHA-256 (BIP-39 checksum), SHA-512 inside HMACNo
    checksumA few extra bits to detect accidental mistakesLast 4–8 bits of the mnemonic, letter case in EIP-55Not the point: it only says "valid / not valid"
    encodingSame information, different representation, no securityBits → words, bytes → hex, lowercase → mixed caseYes, always

    A common confusion is between hashing and encoding: hex or the 12 words can always be converted back, while from the address it is impossible to get back to the public key. Another one is between checksum and hash: EIP-55 uses a hash, but its goal is only to catch typos.

    Why so many different techniques instead of one algorithm?

    At first it seems overcomplicated, but each step needs a property that the others don't have, and no single algorithm has all of them:

    • BIP-39 / BIP-32 / BIP-44 → key management. The problem here is human: backing up and recovering many keys. We need something deterministic (same words, same keys), readable and compatible between wallets. A hash alone could derive keys, but it would not give the tree structure or the standard paths.
    • secp256k1 → the public/private relationship. Only public-key cryptography lets everyone verify a signature without being able to create it. A hash cannot do this: it has no "public" and "private" side. This is also the only step where we want algebraic structure (Homework 1).
    • Keccak-256 → hashing. We need a short, fixed-length identifier that hides the structure of the public key. secp256k1 cannot give this, because its outputs keep the algebraic relations (we saw it with the avalanche test).
    • EIP-55 → error detection. A completely different goal: protecting against human mistakes when copying addresses, with zero cost and full backward compatibility.

    It is the same principle as in software engineering: every component does one job well. It also limits damage: if one primitive were broken (for example the ECDLP by a quantum computer), the others would still do their job, and addresses that never sent a transaction would still hide their public key behind the hash.

    Trying it with a real wallet

    The easiest experiment is to import the public test phrase "test test test test test test test test test test test junk" in a wallet such as MetaMask (on a separate browser profile, and never for real funds) and compare its accounts with the table in tab 1: they match, because MetaMask uses the BIP-44 path m/44'/60'/0'/0/i and increases i for each new account.

    Other things we can notice using wallets:

    • Wallets ask to write the 12 words in order and check them: that is the BIP-39 checksum and encoding at work.
    • When we copy an address it is always in mixed case: that is EIP-55. If we change one letter by hand, many wallets show a warning.
    • Not every wallet uses the same path: some, for example hardware-wallet apps, increase the account level instead of the last index. That is why the same phrase can show different accounts in different wallets, the problem BIP-44 tried to solve.
    • Some wallets support the passphrase ("25th word") and some don't; with a passphrase the same words open a completely different wallet (try it in the sidebar).
